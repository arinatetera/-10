# ЛР5. Переданные отправители и отдельный журнал

Вариант: **Notification**.

## Что дано

Сервис игнорирует переданных отправителей. В `build_service()` разные сервисы получают один и тот же журнал. Основной метод `NotificationService.send()` также нужно реализовать; готовые проверки объектов и зависимостей не переписывайте.

## Задание

### Шаг 1. Сохраните зависимости и настройте сборку

В `NotificationService(senders, outbox)` сохраняйте копию отображения `senders`, но не копируйте сами объекты отправителей. Используйте переданный `outbox`. Пустое отображение не заменяйте стандартным.

В `build_service()` создавайте новый набор отправителей и отдельный `Outbox` для каждого вызова. Вызывайте отправителя один раз, затем проверяйте квитанцию готовой `validate_receipt()` и только после этого записывайте её. Ошибки отправителя передаются вызывающему коду.

### Шаг 2. Реализуйте `NotificationService.send()`

Выберите отправителя по каналу, вызовите `send()` один раз, проверьте квитанцию через `validate_receipt()` и только затем добавьте её в `Outbox`. Неизвестный канал — `UNSUPPORTED_CHANNEL`.

### Шаг 3. Проверьте отказ и следующий вызов

Контрольный исполнитель сначала выбрасывает `DomainError("TEMPORARY")`, затем успешно работает. Первый вызов не повторяется автоматически и не меняет данные; второй использует того же исполнителя. `TEMPORARY` — код учебной проверки, не новая ветка бизнес-логики. Отсутствие зависимости проверяйте через `is None`, а не её истинность.

### Шаг 4. Обязательная практическая часть

В `NotificationService` реализуйте `sent_for_channel(channel)` — кортеж квитанций указанного канала в исходном порядке, и `delivery_summary()` — словарь `{channel: count}` по всем успешным отправкам. Используйте только публичный метод `sent()`, не меняйте `Outbox`.

## Примеры и границы

- Контрольный отправитель возвращает свой текст; именно он попадает в журнал.
- Изменение исходного словаря не меняет сервис; отдельные сборки не делят журнал.
- Явно переданный двум сервисам один `outbox` остаётся общим.
- Ошибка отправителя или `INVALID_DELIVERY` не добавляет запись; неподключённый канал вызывает `UNSUPPORTED_CHANNEL`.
